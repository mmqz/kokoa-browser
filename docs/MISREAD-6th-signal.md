# 又一次误读信号的记录（2026-09-15）

> 这条很短，但值得记 —— 因为它是我第 6 次在同类地方差点出错。

---

## 事情经过

```
后台监视任务 pwsh-14 结束了，报告：
  status: completed
  exit code: 0

我第一反应是「构建成功了」—— 并准备去下载产物验证。

但抓取产物列表时返回【空】，我才去看监视器的原始输出：

  WATCH_EXIT=1
  [stderr] failed to get run: unexpected EOF
```

## 真相

```
· gh run watch 因为【网络错误】退出了（unexpected EOF）
· 那个 exit code 0 是【外层 pwsh 包装命令】的退出码，不是构建的
· 构建【实际还在跑】（status: in_progress，Build 步进行中）
```

## 为什么这值得记

```
「任务完成 + exit code 0」看起来是个明确的成功信号，
但它可能是【工具自己失败】而不是【被测对象成功】。

而我当时的下一步是【下载产物、读元数据、宣布贴牌修好了】——
如果我没注意到产物列表是空的，我会基于一个不存在的产物宣布结论。
```

## 正确的做法（我这次碰巧做了）

```
1. 拿到「结果」后，用【另一个独立查询】确认真实状态
   （我查了 gh run view 的 JSON，看到 status: in_progress）
2. 结果与预期不符时（产物列表为空），【先怀疑链路，不要先解释】
3. 看工具的【原始输出】，而不只看它的退出码
```

## 与之前的关联

```
这是我的第 6 次同类问题，但【性质不同】：

  前 5 次：我【推断】错了（读一点代码就下结论）
  第 6 次：我差点【误读信号】（把工具失败当成被测对象成功）

共同点：都是【没有交叉验证】。
前 5 次是「不验证自己的推断」，这次是「不验证收到的信号」。
```

## 一条可执行的规则

```
【任何「成功」的结论，都要用第二个独立来源确认，才能说出口。】

对构建：不看监视器的退出码，要看 gh run view 的 status/conclusion 字段。
对产物：不假设产物存在，要先列出来。
对我的推断：不凭一段代码下结论，要找第二种证据。
```
