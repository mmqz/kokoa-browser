# 三、我为什么读错了（工具 bug）

## 我的解析脚本有两个错误

```
错误 1：csize 的来源不一致
  我在【本地文件头】里逐个 find(PK\x03\x04) 找条目，
  但 csize 却从【中央目录】读。
  两处的值不一致（en-US 这条：中央目录说 5419，实际内容 5413，差 6 字节），
  于是读出来的内容被截断/错位。

错误 2：我没有交叉验证
  读完得到「69 字节 / 1 行」这个显然不合理的结果时，
  我【没有怀疑工具】—— 一个 5419 字节的条目怎么可能只有 1 行？
  我直接把它当成事实，还据此推出了一个「根因」。
```

# 四、教训（比这个 bug 更重要）

```
1. 结果【明显不合理】时，先怀疑工具，不要先怀疑世界
   「压缩后 69 字节、只有 1 行」—— 这本身就该触发警报

2. 我据此编出了一个「因果链」
   我看到 CI 日志里有「Ensuring that the l10n-central repository exists」，
   就把它和「文案不在包里」【拼成了一个故事】。
   但那条日志是在【另一个时间点】，两者未必相关。
   【这是典型的「先有结论，再找证据」】

3. 正确的做法：换一个独立的方法验证
   这次我换成「在中央目录里列出所有 zen-general 条目、直接看 csize」
   -> 立刻发现 en-US 是 5419 字节，不是 69
   如果我第一轮就这么做，就不会错。
```

# 七、该项目里我第三次「推断错误」

| 次数 | 我推断了什么 | 实际 |
|---|---|---|
| 1 | prefs/*.yaml 经 tools/ffprefs 编译 | 不是（是别的机制） |
| 2 | application.ini 来自 Firefox 模板 | 不是（Zen/surfer 的模板） |
| 3 | l10n-central 覆盖了我们的文案 | **没有（我读错了产物）** |

**三次的共同点：我都在「读源码/日志推断」，而不是「直接验证产物」。**

第 2 次之后我就总结过「要用产物验证假设」；
**这次我确实去读了产物，但读错了 —— 而且没有交叉验证。**

所以教训要加一条：

```
不仅要「用产物验证」，还要「用【两种独立方法】验证产物」。
当结果不合理时，第二种方法不是可选项，是必须的。
```
